# 本次修复与优化说明（2026-11-07）

本目录是在原始包 `nadutong-forum-main.zip` 基础上修出来的可部署版本。原始目录保持未改动，可随时对照。

改动原则：只修真实缺陷、只改必要的性能瓶颈，不重构、不拆分大文件、不改数据表既有字段，因此**不需要手动迁移数据库**（唯一新增的 `invitations` 表由代码在首次使用时自动建表）。

---

## 一、后端（Cloudflare Pages Functions）

### 1. 新增 `GET /api/posts/:id/edits`（原来直接 404）
- 文件：`functions/api/posts/[id]/edits.js`（新增）
- 前端「编辑记录」弹窗一直在调这个接口，但后端从来没有这个文件，点开必定报错。
- 版本号沿用 `edit.js` 的约定：`post_edits` 里存 1..edit_count 的历史快照，`edit_count+1` 是当前版本；返回 `{versions, editCount}`，与前端渲染字段（version/title/content/editorName/at/current）完全对齐。历史表查询异常时仍会返回当前版本，不会整块失败。

### 2. 发帖带投票时，选项写入没有 await
- 文件：`functions/api/posts/index.js` → `createPoll`
- Worker 返回响应后可能立刻被回收，未 await 的 `poll_options` 写入会丢失，表现为「投票只有标题、没有选项、点不了」。
- 改为 `await Promise.all(...)`。

### 3. `/api/invite` 必定 500（读写不存在的列/表）
- 文件：`functions/api/invite.js`（整体重写）+ `functions/api/_invite.js`（新增）
- 原实现读 `users.invite_code`（schema 里没有这一列）、写 `invitations`（schema 里没有这张表）。
- 现在：`ensureInviteTable` 懒建表 + 2 个索引；`inviteCodeOf` 用 FNV-1a 从用户 ID 稳定推导邀请码（`NDT` + 6 位 36 进制），同一用户永远是同一个码，不占新列；`findInviterByCode` 反查邀请人；`recordInvite` 幂等记账并给双方各 +100 分（`INVITE_POINTS`）。
- `/api/invite` 返回 `{code, count, invited, reward}`，与前端邀请卡片字段一致。

### 4. 点赞可以无限刷积分
- 文件：`functions/api/like.js`
- 原来「取消点赞」只删点赞记录和通知，不退积分，于是「点赞→取消→再点赞」可以无限刷。
- 现在取消点赞会扣回 `POINTS_RULE.liked`（`addPointsClamped`，不会扣成负数）。同时把目标存在性校验提前，取消已经没有目标的点赞也能正常退分。

### 5. 首次部署并发请求会 500（`meta.secret` UNIQUE 冲突）
- 文件：`functions/api/_lib.js` → `getSecret`
- 多个并发请求同时发现 secret 不存在，都执行 `INSERT INTO meta`，后者撞 UNIQUE，把注册/登录打成 500。
- 改为 `INSERT OR IGNORE` 后回读已落库的值。

### 6. 发徽章会留下多个「佩戴中」
- 文件：`functions/api/_lib.js` → `grantBadge`
- 授予新徽章时没有清掉旧徽章的 `equipped`，个人主页会同时显示多个佩戴中的称号。
- 现在授予前先 `UPDATE user_badges SET equipped=0 WHERE user_id=?`。

### 7. 签到按 UTC 算日期，凌晨 8 点前签到算「昨天」
- 文件：`functions/api/checkin/index.js`
- 北京时间 00:00–08:00 签到会被判成前一天，「今天已签到」和连续天数都会错。
- 引入 `TZ_OFFSET_MS = 8h`，`dateStr` / `yesterdayStr` 统一按 UTC+8 计算。

### 8. 成员列表 2N 次查询，人一多直接 500
- 文件：`functions/api/users/index.js`
- 原来是「每个用户各查一次佩戴徽章 + 一次档案」，成员到一定数量就会超过 Workers 子请求上限。
- 改为固定 3 次查询：用户表一次、`equipped=1` 徽章批量一次、`user_profiles` 批量一次，再在内存拼装。返回结构与 `publicUserFull` 保持一致（badge/profile 字段不变），管理端无需改动。

### 9. 通知接口无上限全量返回
- 文件：`functions/api/notifications/index.js`
- 前端每 30 秒轮询一次，历史通知越积越多、越用越慢。
- 改为只返回最近 200 条；未读数与总数用一条 `COUNT(*) + SUM(CASE WHEN read=0...)` 单独统计，红点数字仍然准确。

### 10. 帖子列表整表拉回内存再排序分页
- 文件：`functions/api/posts/index.js` → `onRequestGet`
- 旧实现把「全部匹配帖子 + 全站点赞 + 全部回复」拉进内存，归一化后排序再切 20 条，帖子越多越慢。
- 现在把排序分页下推到 SQL（`GROUP BY p.id` + `ORDER BY pinned DESC / 热度表达式 / 最近活动` + `LIMIT ? OFFSET ?`），只把当前页交给 `shapePostList`；**保留一条与旧逻辑完全等价的兜底分支**，SQL 异常时自动回退，不会白屏。
- 热度公式与原 `postHeat()` 完全一致：点赞×3 + 回复×2 + 浏览/10。

### 11. 删帖留下孤儿数据
- 文件：`functions/api/posts/[id].js`
- 原来只删 `replies` / `likes` / `posts`，投票、编辑历史、相关通知全部残留。
- 补上级联清理：`polls` / `poll_options` / `poll_votes` / `post_edits` / `notifications`。
- 附带修掉一个数据统计问题：**作者本人反复打开自己的帖子不再增加浏览量**（原来刷新一次 +1，浏览数虚高）。

### 12. 删账号留下孤儿数据
- 文件：`functions/api/users/[id].js`
- 补上级联清理：该用户的 `poll_votes`、`post_edits`（作者与编辑者两种身份）、名下帖子对应的投票、`user_badges`、`user_profiles`、`checkins`、`push_subscriptions`、`invitations`（邀请人与被邀请人两种身份）。

### 13. 管理员导出漏了 6 张表
- 文件：`functions/api/admin/export.js`
- 原来只导 11 张表，恢复备份会丢徽章、档案、推送订阅、编辑历史、邀请记录。
- `TABLES` 补全为 17 张：新增 `post_edits`、`badges`、`user_badges`、`user_profiles`、`push_subscriptions`、`invitations`。

### 14. 注册：重复账号报 500、昵称不限长
- 文件：`functions/api/auth/register.js`
- `INSERT users` 加 try/catch，把 UNIQUE 冲突转成 409「该账号已被注册」；昵称超过 16 个字直接 400。
- 注册时若带 `invite`，一次性结算邀请奖励，异常不影响注册；返回值增加 `inviteBonus`。

## 七、账号能力增强（本次新增，纯增量）

原本云端账号只能改头像和异人档案，**没有改昵称、改密码，也没有忘记密码的退路**。本次补齐三件事：

1. **用户自助改昵称**：账号页新增「保存昵称」；后端复用已有的 `POST /api/users/:id/profile`（新增可选的 `name` 字段），改完同步 `posts.author_name`、`replies.author_name`，历史帖子不会还挂着旧昵称。登录账号 `login` 不可改。
2. **用户自助改密码**：新增 `functions/api/auth/password.js`，先校验当前密码（PBKDF2 常数时间比对）再重设 hash + salt；新密码至少 6 位，且不能与旧密码相同。
3. **管理员重置他人密码**：`POST /api/users/:id` 新增 `action:'resetpass'`，成员管理列表每行多一个「🔑 重置密码」。这是没有邮箱/手机号的情况下、忘记密码的唯一找回路径。

兼容性（对照「不影响已经注册的人」）：

- **零 schema 变更**：没有加列、没有改表、没有新索引；本次只新增 1 个函数文件，其余都是在已有文件里加字段和界面。
- **密码哈希与 token 格式完全未动**：仍是 PBKDF2-SHA256 / 100000 轮 / 256 位，salt 仍是 `crypto.randomUUID()`；token 结构、签名密钥、30 天有效期不变，**已登录的用户不会被踢下线**。
- **改名只写 `users.name`**，不动 `login` / `points` / `pass_hash` / `salt` / `role` / `created_at`；其他用户的数据完全不受影响。
- 历史通知里的 `actor_name` 是快照，不回改（避免批量改写通知表），需要的话可以后续再做。

已知限制：改密码后，该用户在其它设备上已签发的 token 仍然有效（没有会话表，无法单点踢人）。要做到「退出所有设备」需在 `users` 增加 `token_version` 列、在鉴权时比对，属于可选下一步；本次没有动全站鉴权热路径。

验证：42 个 JS 全部 `node --check` 通过；改昵称 / 改密码的 UPDATE 语句在 SQLite 实测通过（并逐列断言老用户其余字段未变）。

## 八、徽章炫彩效果扩展（+2 种）

原有 6 种（0 金辉 / 1 紫电 / 2 烈焰 / 3 青碧 / 4 彩虹 / 5 银辉）都是亮色渐变 + 统一白色扫光，整体偏同一路。新增两种方向不同的：

- **6 墨曜（深色星砂）**：深墨蓝黑底 + 两团蓝紫雾光 + 六点星砂明暗闪烁，是全站唯一的深色徽章效果，和六种亮色系一眼能分开。
- **7 烟粉（呼吸光晕）**：粉白渐变 + 呼吸式光晕，并主动关掉全站统一的白色扫光——因为扫光正是「彩虹/银辉」最显眼的特征，关掉后才不会撞脸。

实现方式（沿用项目已有的安全边界）：

- 只改 `_lib.js` 里 `BADGE_EFFECTS` 这个纯字符串校验数组（`'0'..'5'` → 追加 `'6','7'`），**没有碰 `BADGE_SEEDS`**——历史上往徽章种子里加东西会导致 `ensureSchema` 失败、全站 500。
- 新样式单独放在 `assets/css/badge-effects-extra.css`，不改 `main.css`（不覆盖线上大文件），在 `index.html` 里追加一行 `<link>`。
- 前端只在 `BADGE_EFFECT_OPTIONS` 里加两项，徽章管理弹窗的色卡从 6 个变 8 个。
- 效果继续走原有变量机制（`--be-bg / --be-ink / --be-edge / --be-glow`），所以小徽章、徽章墙、发放格、管理列表行四处展示会自动生效，不需要改渲染函数。

注意：老访客如果还加载着旧 CSS，带新效果的徽章会暂时显示成无底色，`?v=40` 刷新后正常；**已创建的旧徽章完全不受影响**，新效果只在管理后台新建或编辑徽章时可选。

### 2. 回帖与楼中楼显示徽章（bug 修复）

现象：发帖的时候作者徽章正常，回复 / 楼中楼里没有。

排查结果：后端其实一直在返回 —— `_lib.js` 的 `shapeReplyList` 里有 `authorBadge:info.badge||null`，`userInfoMap` 也会批量取佩戴中的徽章；前端 `rootHtml`（顶层回答）与 `subReplyHtml`（楼中楼，递归子回复）模板里也都写了 `${badgeHtml(...)}`。

真正的原因在前端**取数据后重组对象**时把字段丢了：`app.js` 里有两处把接口返回的 reply 逐字段抄进本地对象，字段表是手写的，两处都漏了 `authorBadge`：

- 帖子详情首屏渲染那处（`replies=(d.replies||[]).map(...)`）
- `cloudRerender()` 里重新拉数据那处（`replies=(d.replies||[]).map(...)`）

所以徽章在"刚发帖、数据还是接口原样"的时候能显示，一旦重新渲染就消失。修复就是在两处映射各补一个 `authorBadge:r.authorBadge||null`，模板不用动，顶层回答和楼中楼（含更深层子回复）会一起恢复显示。

## 十、界面细节：骨架屏 / 列表逐条入场 / 数字滚动

这三项都放在**新文件**里，是个纯增量改动：`assets/css/ui-polish.css` 负责样式，`assets/js/ui-polish.js` 负责数字逻辑。样式没有往 `main.css` 里加，逻辑也没有去改 app.js 的渲染函数（只有一处：把云端列表的加载提示换成了骨架卡片的 HTML 字符串）。

### 1. 骨架屏

以前云端论坛要等接口返回，页面上只有一行「正在从云端加载帖子…」，内容进来时是整块突变。现在进列表先摆 4 张骨架卡片（左侧投票块 + 三行文字条 + 作者行），灰条上跑一道微光，真实数据到了再整体替换。

- 灰条颜色走主题变量 `--pt-soft / --pt-panel / --pt-border`，深浅色主题都成立；
- 四张卡片的微光依次错开 0.12s，看起来是一条光在往下扫，而不是四张一起闪；
- 原来的加载文字保留成骨架下方一条弱化小字，信息没丢。

### 2. 列表逐条入场

列表项（`.q-item`）改成出现时淡入 + 上移 10px，`nth-child` 依次错开 45ms，最多堆到 480ms 就封顶，深列表不会越滚越慢。

### 3. 数字滚动

`ui-polish.js` 用一个 `MutationObserver` 盯着 `#app`，只认这几类节点：`.vote-count`（赞数）、云端账号卡里的「积分」、个人空间卡里的积分。**第一次见到只记基准值不动**，之后数值一变就从旧值递增到新值（ease-out，320–900ms，差值越大滚得越久），结束时轻微放大回弹一次。

几个必要的边界：

- 赞数节点用所属按钮的 `data-vote / data-avote` 作为 key，列表重渲染换了节点也能接着比，不会错误地从 0 开始滚；
- 正在动画的节点带 `data-num-anim` 标记，会被跳过，避免自己触发的 DOM 变化把自己再扫一遍；
- 云端账号卡里 `等级（Lv12）/ 称号` 这两格虽然也是数字，但已经排除掉了——否则三个格子共用一个 key 会互相打架；
- 系统开启「减少动态效果」时，骨架、入场、滚动全部关闭。

### 4. 已知没覆盖的地方

「加载更多」那一步没有骨架（它是在已有列表下面追加，用按钮的 loading 状态即可）；回复数嵌在「💬 12 个回答」这种带文字的句子里，没有单独做滚动。这两处要做得加标记，考虑到收益不大，本次没有动。

## 十一、三个占卜模块的界面与动画

改之前先把三个页面在线上逐个打开看过，结论是配色没问题，缺的是「过程感」——三个模块全都是点一下直接出结果，中间没有任何可看的东西；黄大仙的问题最重，点完之后那一屏基本是空白的。

这一轮仍然守住原来的两条线：**不改 `main.css`，不改 `app.js`**。新增 `assets/css/divination-polish.css` 与 `assets/js/divination-polish.js` 两个文件，`index.html` 各加一行引用，版本号 `?v=42` → `?v=43`。脚本只用 `MutationObserver` 盯着 `#app`，看到对应页面的 DOM 出现再补自己那一块。

### 1. 三个模块各自的主视觉色

原来三个页面的头部是同一套壳：同样的橙色小标签、同样的无衬线大标题，只有伏羲那个用了径向渐变（`.yj-head` 里读的是 `--yj-accent`，而塔罗和黄大仙没定义这个变量，渐变其实是失效的）。

现在按路由给每个模块一个强调色——`.portal--yijing` 赭红、`.portal--tarot` 夜空紫、`.portal--huang` 朱砂——直接覆盖 `--yj-accent` 这个既有变量，头部渐变、标签、装饰线就一起跟着变了，不需要重写任何一条既有规则。标题只加了字重和一点标题下的渐隐装饰线，**字体沿用站点默认字族**：第一版试过换成宋体/衬线（`Noto Serif CJK SC` 那一串），但用户机器上这些字族都没装、回退也落不到宋体上，反而出现字体不显示的问题，所以改回默认，靠配色和装饰线区分三个模块就够。

### 2. 伏羲六十四卦

- **六爻爻位盘**（`.dj-slots`）：脚本在 `#yj-throws` 前面插一组六格，初爻到上爻各一格，投掷前是虚线占位，投出来一爻填一格；阳爻画一整条、阴爻断成两条，动爻（6 老阴 / 9 老阳）整格提亮。原来投掷前那一块是完全空的，看不出要投几次、投到第几爻了。原来的文字标签（`初爻：8` 那种）在爻位盘建好之后隐藏，信息不重复。
- **四种结果都有动画**：原 CSS 里的 `yjCoinFlip` 只挂在 `.yj-coin-6` 和 `.yj-coin-9` 上，而三枚铜钱出 6、7、8、9 的概率是 1/8、3/8、3/8、1/8——也就是说四分之三的投掷点了按钮没有任何反馈。现在每一爻填入时都走一次翻面（`djSlotIn`）。
- **结果区错峰**：本卦 → 变卦 → 互卦 → 错卦 → 综卦 五栏按 0.02 / 0.14 / 0.26 / 0.38 / 0.5 秒依次淡入，不再一次性糊上来。
- **动爻呼吸**：`.yj-line-row .moving .yj-yang` 加了 2.6 秒一轮的光晕呼吸，比原来那条死板的 `0 0 0 2px` 描边更容易看出哪一爻在动。

### 3. 塔罗占卜

- **牌背与翻牌**：`.tc-face` 原来只是一块写着牌名和释义的白卡片。脚本往 `.tc-inner` 里补一层 `.tc-back`（深紫底 + 45° 斜纹 + 中心菱形），抽牌时先出现牌背，再翻成牌面。
- **翻牌不用 `backface-visibility`**：一开始按标准 3D 写法做的（`preserve-3d` + `backface-visibility:hidden`），本地渲染时牌面被牌背整块盖住、怎么调都翻不过来。改成两段式：牌背转到 88° 消失、牌面从 −88° 转正（`djBackOut` / `djFrontIn`），不依赖浏览器的 3D 背面剔除，行为确定。牌背默认 `opacity:0`，所以动画被关掉时直接看到牌面，不会出现"两张叠一起"。
- **逆位终于有视觉区分**：`main.css` 里 `.tarot-card.rev .tc-front` 是一条**空规则**（只写了注释「不旋转，仅用文字标注逆位」），所以逆位和正位只差一行小字。现在给逆位牌加暗红描边 + 右上角朱印「逆」+ 逆位标签与关键词一起转暗红。牌面本身按既有约定不旋转，避免文字倒置。
- **牌阵选中态**：从「只有一圈边框」加强成底色 + 强调色边框 + 阴影，四张牌阵并排时能看清选了哪个。

### 4. 黄大仙灵签

- **签筒摇签**：结果出现时脚本往 `.huang-result` 里盖一层 `.dj-veil`（签筒 + 五支签 + 一支签弹出），筒身按 `djShake` 左右摇，签在 0.45 秒后弹出来，整层 1.3 秒后淡出揭晓。签筒是纯 CSS 画的（筒身渐变 + 椭圆筒口 + 落地阴影），没有加图片资源。
- **签纸**：`.huang-result` 从普通卡片改成米黄纸底 + 纸边阴影，签号做成倾斜的朱印，签文装进一个淡底框里、**横排左往右读**（签文原文用 `\n` 分句，用 `white-space: pre-line` 保留换行，居中排列，读起来是一句一行）。第一版做成竖排（`writing-mode: vertical-rl`），用户反馈横排更好读，遂改回横排。典故用虚线与正文分隔。
- **五档等第重配**：原来的 `lv-上上 / 上吉 / 中吉 / 中平 / 下下` 是 Bootstrap 那套淡色块，其中「下下」用的 `#D6DBDF` 灰蓝跟全站橙色主题完全不搭。现在换成金 / 朱 / 青 / 墨 / 浓墨五档，跟签纸的色调统一。
- 既有的一个好处保留了：`readings` 会按你问的事自动展开对应那一栏（问工作就展「事业」），只是原来没有任何提示，现在靠签纸的整体样式让它显眼一些。

### 5. 两个防重复与降级处理

- 同一支签、同一副牌重新进入页面时不再摇第二次、翻第二次：牌面签名和签文签名记在 `sessionStorage`，一致就跳过仪式。
- 系统开启「减少动态效果」时，爻位翻面、结果错峰、动爻呼吸、翻牌、摇签、遮罩全部关掉，直接显示最终状态（`.dj-veil` 直接不渲染）。

### 6. 验证方式

`node --check` 通过；本地把 `main.css` + 新 CSS + 新 JS 一起内联进预览页（`file://` 下跨目录加载外部 CSS/JS 会被 CORS 拦，必须内联），用真机截图逐项看过：爻位盘的空位/已填/动爻三种状态、结果五栏、塔罗正位与逆位两张牌的差别、签纸与横排签文、签筒形态。自动化浏览器里 CSS 动画不会推进（入场动画停在首帧、`opacity:0` 的元素看不见），所以静态验收都是先关掉动画再截图，这一点在预览页里用临时覆盖样式处理，没有带进交付文件。

版本号在两次交付里升了两次：`?v=42` → `?v=43`（首版交付）→ `?v=44`（字体与签文排向修正）。

## 十二、邀请里程碑徽章没生效（接引人 / 哪都通HR）

**现象**：用户反馈「拉 1 人得接引人、拉 5 人得哪都通 HR，但没有生效」，并怀疑是自己后来编辑徽章炫彩动效导致抓取不到。

**排查结论**：与炫彩效果无关。`BADGE_EFFECTS` 只决定徽章的颜色动效，和发放条件没有任何关系。
线上 `GET /api/badges` 里确实存在两枚 `kind='auto'` 的徽章：

- `inviter_1` 接引人 🤝 effect=5（银辉）
- `inviter_5` 哪都通HR 💼 effect=10（靛蓝）

但整个后端**没有任何地方调用 `grantBadge` 发放它们**：`recordInvite()` 只写了邀请关系、给双方各加 100 积分就结束了。也就是说这条规则从来只是「写在库里的两行数据」，没有对应的代码，所以邀请多少次都不会发徽章。

**修复**（`functions/api/_invite.js` + `functions/api/invite.js`，不改 `_lib.js`、不改前端）：

1. `INVITE_BADGES` 定义两个阈值（1 人 / 5 人），`effect` 沿用线上已有值，不覆盖用户已调好的动效。
2. `ensureInviteBadges()` 只补缺失的徽章行（先 `SELECT` 判断再 `INSERT OR IGNORE`），避免每次请求都白写一次库。
3. `syncInviteBadges()` 按 `invitations` 实际行数发徽章，复用已有的幂等 `grantBadge`（已拥有直接跳过，并写一条 `badge` 通知 + 尝试 Web Push）。
4. `recordInvite()` 末尾调用一次 `syncInviteBadges`，新人注册当场发放。
5. `GET /api/invite` 也调用一次，**老用户之前漏发的徽章，打开邀请面板就会补上**；同时多返回 `badges`（哪几档已拿到）与 `justGranted`（这次刚补发的），前端旧代码不读这些字段也不受影响。

**验证**：`node --check` 两个文件均通过；`_audit/invite-badge-test.py` 用 SQLite 复现同一条 SQL 链路，邀请 7 人——第 1 人只发 `inviter_1`、第 5 人发 `inviter_5`、其余不发；重复 `sync` 不再发徽章也不再写通知；始终只有一枚 `equipped=1`（最新是 HR）；空库能自动补出两枚徽章。输出 `ASSERT OK`。

**注意**：`grantBadge` 的既有语义是「新徽章自动佩戴并清掉其它徽章的佩戴标记」，所以拿到 HR 时会顶掉之前佩戴的称号——这和活动徽章「我来也」的行为一致，如果要改成「只发不自动戴」需要另动 `grantBadge`，本次没动。

**补充（历史邀请怎么补）**：`invitations` 表里已有的记录不会被抹掉，人数是现算的，所以之前拉过的人照样计入。
为了让「不打开邀请面板的人」也能自动补到，又在 `functions/api/auth/me.js` 里加了一次同步：
每次登录/刷新当前用户（前端 `Cloud.refresh()`，App 打开也会走）都会顺带补发，补到的徽章会直接出现在这次返回的 `user.badge` 里。
`syncInviteBadges` 改成先 `SELECT COUNT(*)` 再决定是否继续：没邀请过人的用户只多一次只读查询，不碰 `badges` 表；
`invitations` 表还没建过的库直接当 0 处理，不会在热路径上建表。

## 十三、手机端适配打磨（v45）

**背景**：站点原本已有手机断点（`@media(max-width:680px)` 里做了顶栏吸顶、导航横滑、弹窗改底部抽屉、聊天窗高度随 `--mobile-chrome-h` 伸缩），但还有几处手机上会硌手的地方：输入框字号偏小会被 iOS 一聚焦就整页放大、帖子标题行内写死 23px 偏大、帖子头部的操作按钮用 `margin-left:auto` 顶行尾导致「分享」单独掉一行、横向导航被截断却没有「还能往右滑」的提示、弹窗打开时手指一动背景整页跟着滑、刘海屏与底部手势条会压住内容。

**做法**：不碰 `main.css`、不碰 `app.js`，新增两个独立文件，只在手机宽度生效（桌面端完全不变）：

1. `assets/css/mobile-polish.css`（覆盖式补丁，7 节，全部包在媒体查询里）
   - 触控：`touch-action:manipulation` 去掉双击缩放与 300ms 点击延迟；`-webkit-tap-highlight-color:transparent` 去掉灰块；`@media(hover:none)` 下按下有 `scale(.975)` 回弹（`prefers-reduced-motion` 时取消）。
   - 输入：680 以下 `input/select/textarea/.field` 统一 16px，防 iOS 自动放大。
   - 触控目标：`.qm/.rp-btn/.chat-time-node/.p-crumb a/.tag` 最小 28px 高，`.vt` 40px，`.btn-sm` 32px。
   - 文本：`.p-panel/.answer/.a-body/.q-main` 加 `overflow-wrap:anywhere`；图片/视频/iframe `max-width:100%`；`pre` 换行、表格改整块横滑，不把页面撑出横向滚动条。
   - 帖子排版：`.p-panel` padding 收到 16/14、卡片圆角 10px；`>h2` 压到 19px（`!important`，因为模板是行内 `style="font-size:23px"`）；`.q-meta` 允许换行、按钮降字号、取消 `margin-left:auto`，操作按钮自然跟随信息区换行；`≤380px` 再降一档。
   - 横滑导航：隐藏滚动条、`scroll-padding`，并用 `mask-image` 在两端做渐隐（**用 mask 而不是覆盖层**，所以不挡点击；属性由 JS 按真实滚动位置切换，滑到头就不提示）。
   - 安全区：顶栏补 `env(safe-area-inset-top)`，`.p-main`/`.modal`/`.wx-input-wrap` 补 `env(safe-area-inset-bottom)`。
   - 平板：681–1024 之间侧栏 176px、`.p-main`/`.p-panel` 收紧，避免正文被挤。
   - 滚动：`-webkit-overflow-scrolling:touch`；横滑容器 `overscroll-behavior-x:contain`。

2. `assets/js/mobile-polish.js`（IIFE，只在 `max-width:680px` 生效）四件事：
   - 弹窗打开时 `body` 改 `position:fixed` + `top:-scrollY` 锁背景滚动，关闭后复原并 `scrollTo` 回原位置（**不动 `overflow`**，`app.js` 自己管那一条，互不打架）。
   - 双击顶栏（`.portal-top`/`.topbar`）平滑回到顶部；点在 `.p-logo/.user-chip/a/button/input/.side-item` 上不触发。
   - 输入框聚焦后 280ms 用 `visualViewport` 判断是否被软键盘挡住，被挡才 `scrollIntoView({block:'center'})`。
   - 横向导航：`hashchange` 后把 `a.on` 滚到中间；并给每个 `.nav` 加滚动监听，按 `scrollLeft` 计算左右是否该显示渐隐（`data-mpf` 属性），用 `MutationObserver` 在路由重建导航后自动补绑。

3. `index.html`：加 `mobile-polish.css?v=45` 与 `mobile-polish.js?v=45` 两个引用，并把原有 8 处 `?v=44` 一起升到 `?v=45`（缓存必须刷新，否则手机拿到的还是旧 CSS）。

**验证**：`node --check mobile-polish.js` 通过；390×844 内嵌预览（`_audit-frame.html` + 本机 `http.server 8123`）下首页与登录页 `documentElement.scrollWidth=390`，无横向溢出；登录页输入框计算字号=16px；`.nav` 计算 `mask-image` 生效且 `data-mpf="r"`；手动插入 `.modal-mask` 后 `body.style.position=fixed`、移除后回到 `static` 且 `scrollWidth` 不变；帖子页组件按真实模板类名做静态对照（标题 19px、长链接自动折行、操作按钮不再被 `auto` 顶到行尾）。

**已知取舍**：`touch-action:manipulation` 会关掉「双击放大」（仍可双指捏合放大），这是为了去掉双击误放大与点击延迟；若更看重无障碍缩放，可以删掉这一行。iOS 上弹窗锁背景用的是 `position:fixed` 方案（`overflow:hidden` 在 iOS 拦不住背景滚动）。
## 十四、手机端深度适配 + 桌面端宽屏（v46）

**背景**：这一版手机端访问量比桌面大，用户希望手机端再深一层；桌面端他自己用得多，也希望能"读起来不那么累"。原站点手机断点基本齐全（吸顶、横滑导航、底部抽屉弹窗、聊天窗自适应），这一轮补的是"用起来会硌手"和"看不清"的地方。

**做法**：仍然不碰 `main.css`、不碰 `app.js`。新增 `assets/css/pro-polish.css` 与 `assets/js/pro-polish.js`，并把阻塞首屏的外部字体去掉。

1. **去掉外部字体请求（性能）**
   `index.html` 原来在 `<link rel="stylesheet" href="https://miaoda.feishu.cn/fonts/css2?family=Noto+Sans+SC...">` 上加载思源字体。这是 CSS 阻塞资源，手机上要等一次跨站连接（DNS + TLS + 字体文件），首屏会被拖住；而且这台机器上它本来就没成功（用户之前说过"字体不显示"）。
   现在整行删掉，`main.css` 的 `--sans` 会自然回退到 `PingFang SC` / `微软雅黑` / `system-ui` —— 也就是用户目前实际看到的那套系统字体，观感不变，但少一次阻塞请求。

2. **图片点开全屏查看（新功能）**
   帖子正文（`.inline-img`）和聊天里的照片（`.msg-photo`）原来只有 `cursor:zoom-in` 的样式，**没有任何点击行为**，点上去什么都不会发生；聊天里的图最大只有 180px，收到一张糊成一团的图没法看大。
   现在点任意一张 → 黑底 94% 全屏查看，图按比例 `object-fit:contain` 铺满；再点图片本身放大 1.8 倍，点遮罩空白、按 Esc、或在手机上往下拖 90px 都能关掉。整个查看器由 JS 自己创建，关掉后把 `body` 的 `overflow` 还原成打开前的值。

3. **回到顶部悬浮球（仅手机）**
   滚动超过 520px 后右下角淡入一个 44×44 的 ↑ 球，点击平滑回顶。
   位置带 `env(safe-area-inset-bottom)`；另外当页面存在 `.wx-input-wrap` / `.chat-input-row`（聊天、回复输入栏）时自动抬高到 96px，避免压在发送按钮上。

4. **高内容弹窗自动变全屏抽屉（仅手机）**
   徽章管理、编辑资料这类长表单，原来挤在 88vh 的底部卡片里，卡片内再滚一层，手指很容易滑到外面。
   现在 `.modal` 内容高度超过视口 78% 时自动加 `ndp-full`：高度 92dvh、顶部圆角、底部补安全区，滚动只发生在卡片内部。

5. **手机横屏**
   `max-height:520px` 的横屏下顶栏压到 46px，隐藏 logo 副标题与用户等级小字，导航条 padding 收紧，把高度让给正文。

6. **桌面宽屏内容不再无限拉长（≥1680px 才生效）**
   1680 以上的屏，帖子正文一行能拉到 1800px 宽，眼睛要来回扫。现在 `.p-crumb / .p-panel / .room-tabs-bar / .wx-im` 限宽 1240px 并居中，背景仍然铺满、左右留白对称。
   这条只在 1680px 以上生效，1440 及以下和原来完全一样。

7. **桌面端细节**
   滚动条统一成 10px 细条 + 半透明圆角（原来默认是系统粗条）；给可点击元素补 `:focus-visible` 焦点框（Tab 键走页面时能看清停在哪，鼠标点击不触发；输入框不加，避免和自身边框叠成双层）。

**验证**：`node --check pro-polish.js` 通过；`index.html` 13 处版本号统一为 `v=46`、`v=45` 残留 0、`Noto/miaoda` 残留 0；390×844 内嵌预览实测——点 `.inline-img` 后 `#ndp-viewer` 创建且 `display:flex`、`class=on`，点遮罩后 `display:none`；滚动页到 2090px 后 `#ndp-top` 类名变为 `on`，点它后 `scrollY` 回到 0；注入 24 行的高弹窗后 `.modal` 类名变为 `modal ndp-full` 并按 92dvh 铺满；桌面宽屏规则在视口不足 1680 的环境下没法截图，只做了 CSS 解析确认（同文件后面的规则都正常生效，说明该媒体块语法没问题）。

**已知取舍**：
- 去掉外部字体后，Windows 上看到的是微软雅黑而不是思源黑体；如果反而更喜欢思源，把 `index.html` 里那一行加回来即可（代价是手机首屏多一次外部请求）。

## 十五、收藏 / 草稿 / 楼层直达 / 消息合并（v47）

**背景**：这一轮按用户选定的四项做，全部落在纯前端，不碰云端额度，也不改 `app.js`、`main.css` 一个字。

**做法**：新增 `assets/css/pro-tools.css` 与 `assets/js/pro-tools.js`，用 MutationObserver 在路由重绘后增量注入，脚本出问题也只影响自己，原站逻辑不受牵连。

1. **帖子收藏（稍后再看）**
   帖子详情操作行多一个「☆ 收藏」，点一下变「★ 已收藏」，再点取消。左侧导航「帖子消息」下面多一个「★ 我的收藏」入口（手机端那条横滑导航里同样有），点开是收藏列表，可以点标题跳回帖子、也可以单条「移除」。
   数据存在浏览器 localStorage 的 `ndt_favs_v1`，**只在本机、不上云**，换设备或清缓存就没了——面板里也把这句话写清楚了。

2. **草稿自动保存**
   发帖页的「标题 / 内容」、帖子下的「写下你的回答」、楼中楼回复框，停止输入约 0.7 秒就自动存一份草稿，字段下方出现「草稿已自动保存 · 时间」，带一个「清空草稿」。
   下次再进同一个位置（同一篇帖子的回答框、同一个楼中楼的回复框各自独立），字段还是空的就自动填回上次的内容，提示条写「已恢复上次未提交的草稿」。点「发布」「提交回答」「发送」之后自动清掉对应草稿。草稿保留 7 天，过期自动丢弃。

3. **楼层直达 + 楼号**
   回答区标题下多一条「楼层直达 [输入框] [跳转] · 共 N 层」；每个回答的作者信息行末尾加了「1 楼 / 2 楼…」小标。
   输入序号回车或点跳转，滚到那一楼并闪两下高亮。滚动用的是 `scrollIntoView`，个别老浏览器不平滑，420ms 后自动补一次无动画的定位。

4. **消息中心同类合并**
   云端消息中心里原来一条点赞一个条目，被点赞几次就刷几条。现在同一篇帖子的点赞自动合成一条：标题变成「王也、诸葛青 等 4 人赞了你的帖子」，后面挂一个「已合并 4 条」，并多一个「全部标为已读」把这批一起清掉。
   回复类通知内容各不相同，不合并；离线版消息中心本来就带计数，也不动。
   工具栏加了「合并同类」开关，关掉立刻还原成一条一条的原样（原文本在合并前就备份下来了），开关状态存 `ndt_merge_kind_v1`。

**验证**：`node --check pro-tools.js` 通过；`index.html` 15 处版本号统一 `v=47`、`v=46` 残留 0。用与真实站点同结构的静态页面在浏览器里跑了一遍：注入结果「楼层条 1 / 楼号 3 / 收藏入口 1 / 收藏按钮 1 / 合并开关 1」；点收藏写入 `{"id":"p1",...}` 且按钮变「★ 已收藏」、侧栏红点变 1；收藏面板打开列出 1 条、移除后清空；输入标题 0.7 秒后写入草稿并在重载后自动填回、提示「已恢复上次未提交的草稿」；点发布后草稿键消失；4 条同帖点赞合并成「王也、诸葛青 等 4 人赞了你的帖子」+「已合并 4 条」+ 3 条隐藏 + 「全部标为已读」，关掉开关后标题还原成「王也 赞了你的帖子」且隐藏条目重新显示；跳楼后目标楼拿到 `.ndf-hl` 高亮。390×844 手机宽度下同一套断言全部通过，收藏面板自动变成底部抽屉。

**已知取舍**：
- 收藏只在本机，没有做云端同步（云端额度不划算，且会牵动后端表结构）。
- 草稿在点「发布」的瞬间就清掉；如果那次发布被校验拦下，内容还在输入框里，但草稿记录已经没了（接着输入会重新存）。
- 合并只处理「点赞」，回复通知保持一条一条（回复内容各不相同，合并后没法看出谁说了什么）。

## 十六、v48：收藏入口不再"闪一下" + 手机端论坛视觉打磨

**起因**：用户反馈两点——① 点别的板块时，左边"我的收藏"会先消失再出现，观感不好；② 手机上论坛那块还要再顺一版，诉求是"视觉看着舒服"。

### 1. "我的收藏"闪没：原因与改法

`app.js` 的 `portalShell()`（L1742）每切换一次路由就把整个侧栏重建一遍，注入的 `.ndf-fav-entry` 随之被抹掉；`pro-tools.js` 原来靠 MutationObserver + 180ms 去抖再补回来，这 180ms 就是肉眼看到的"消失一下"。

改法：MutationObserver 的回调本来就跑在浏览器绘制之前（微任务），所以不再等去抖——回调里先同步补回侧栏入口（`repinSide()`），其余工作（草稿恢复、楼层条、消息合并）仍然走去抖，并且从 180ms 收紧到 90ms；`hashchange` 也改成"先补入口、再延后跑剩下的"。

**实测**：在本地造了一个与真实侧栏同结构的页面，把侧栏整体换成不含入口的新内容，再用 MutationObserver 记录入口回来的耗时——`delta = 0ms`，即同一轮微任务内就恢复了，不会有一帧缺失。

### 2. 手机端论坛视觉打磨（新增 `pro-forum.css` + `pro-forum.js`）

原则：只覆盖不改原文件，全部规则锁在 `max-width:680px`（外加 380 小屏一档），桌面与平板完全不受影响。
