# 本次修复与优化说明（2026-11-07）

本目录是在原始包 `nadutong-forum-main.zip` 基础上修出来的可部署版本。原始目录保持未改动，可随时对照。

改动原则：只修真实缺陷、只改必要的性能瓶颈，不重构、不拆分大文件、不改数据表既有字段，因此**不需要手动迁移数据库**（唯一新增的 `invitations` 表由代码在首次使用时自动建表）。

---

## 一、后端（Cloudflare Pages Functions）

### 1. 新增 `GET /api/posts/:id/edits`（原来直接 404）
- 文件：`functions/api/posts/[id]/edits.js`（新增）
- 前端「编辑记录」弹窗一直在调这个接口，但后端从来没有这个文件，点开必定报错。
- 版本号沿用 `edit.js` 的约定：`post_edits` 里存 1..edit_count 的历史快照，`edit_count+1` 是当前版本；返回 `{versions, editCount}`，与前端渲染字段（version/title/content/editorName/at/current）完全对齐。历史表查询异常时仍会返回当前版本，不会整块失败。

### 2. 发帖带投票时，选项写入没有 await
- 文件：`functions/api/posts/index.js` → `createPoll`
- Worker 返回响应后可能立刻被回收，未 await 的 `poll_options` 写入会丢失，表现为「投票只有标题、没有选项、点不了」。
- 改为 `await Promise.all(...)`。

### 3. `/api/invite` 必定 500（读写不存在的列/表）
- 文件：`functions/api/invite.js`（整体重写）+ `functions/api/_invite.js`（新增）
- 原实现读 `users.invite_code`（schema 里没有这一列）、写 `invitations`（schema 里没有这张表）。
- 现在：`ensureInviteTable` 懒建表 + 2 个索引；`inviteCodeOf` 用 FNV-1a 从用户 ID 稳定推导邀请码（`NDT` + 6 位 36 进制），同一用户永远是同一个码，不占新列；`findInviterByCode` 反查邀请人；`recordInvite` 幂等记账并给双方各 +100 分（`INVITE_POINTS`）。
- `/api/invite` 返回 `{code, count, invited, reward}`，与前端邀请卡片字段一致。

### 4. 点赞可以无限刷积分
- 文件：`functions/api/like.js`
- 原来「取消点赞」只删点赞记录和通知，不退积分，于是「点赞→取消→再点赞」可以无限刷。
- 现在取消点赞会扣回 `POINTS_RULE.liked`（`addPointsClamped`，不会扣成负数）。同时把目标存在性校验提前，取消已经没有目标的点赞也能正常退分。

### 5. 首次部署并发请求会 500（`meta.secret` UNIQUE 冲突）
- 文件：`functions/api/_lib.js` → `getSecret`
- 多个并发请求同时发现 secret 不存在，都执行 `INSERT INTO meta`，后者撞 UNIQUE，把注册/登录打成 500。
- 改为 `INSERT OR IGNORE` 后回读已落库的值。

### 6. 发徽章会留下多个「佩戴中」
- 文件：`functions/api/_lib.js` → `grantBadge`
- 授予新徽章时没有清掉旧徽章的 `equipped`，个人主页会同时显示多个佩戴中的称号。
- 现在授予前先 `UPDATE user_badges SET equipped=0 WHERE user_id=?`。

### 7. 签到按 UTC 算日期，凌晨 8 点前签到算「昨天」
- 文件：`functions/api/checkin/index.js`
- 北京时间 00:00–08:00 签到会被判成前一天，「今天已签到」和连续天数都会错。
- 引入 `TZ_OFFSET_MS = 8h`，`dateStr` / `yesterdayStr` 统一按 UTC+8 计算。

### 8. 成员列表 2N 次查询，人一多直接 500
- 文件：`functions/api/users/index.js`
- 原来是「每个用户各查一次佩戴徽章 + 一次档案」，成员到一定数量就会超过 Workers 子请求上限。
- 改为固定 3 次查询：用户表一次、`equipped=1` 徽章批量一次、`user_profiles` 批量一次，再在内存拼装。返回结构与 `publicUserFull` 保持一致（badge/profile 字段不变），管理端无需改动。

### 9. 通知接口无上限全量返回
- 文件：`functions/api/notifications/index.js`
- 前端每 30 秒轮询一次，历史通知越积越多、越用越慢。
- 改为只返回最近 200 条；未读数与总数用一条 `COUNT(*) + SUM(CASE WHEN read=0...)` 单独统计，红点数字仍然准确。

### 10. 帖子列表整表拉回内存再排序分页
- 文件：`functions/api/posts/index.js` → `onRequestGet`
- 旧实现把「全部匹配帖子 + 全站点赞 + 全部回复」拉进内存，归一化后排序再切 20 条，帖子越多越慢。
- 现在把排序分页下推到 SQL（`GROUP BY p.id` + `ORDER BY pinned DESC / 热度表达式 / 最近活动` + `LIMIT ? OFFSET ?`），只把当前页交给 `shapePostList`；**保留一条与旧逻辑完全等价的兜底分支**，SQL 异常时自动回退，不会白屏。
- 热度公式与原 `postHeat()` 完全一致：点赞×3 + 回复×2 + 浏览/10。

### 11. 删帖留下孤儿数据
- 文件：`functions/api/posts/[id].js`
- 原来只删 `replies` / `likes` / `posts`，投票、编辑历史、相关通知全部残留。
- 补上级联清理：`polls` / `poll_options` / `poll_votes` / `post_edits` / `notifications`。
- 附带修掉一个数据统计问题：**作者本人反复打开自己的帖子不再增加浏览量**（原来刷新一次 +1，浏览数虚高）。

### 12. 删账号留下孤儿数据
- 文件：`functions/api/users/[id].js`
- 补上级联清理：该用户的 `poll_votes`、`post_edits`（作者与编辑者两种身份）、名下帖子对应的投票、`user_badges`、`user_profiles`、`checkins`、`push_subscriptions`、`invitations`（邀请人与被邀请人两种身份）。

### 13. 管理员导出漏了 6 张表
- 文件：`functions/api/admin/export.js`
- 原来只导 11 张表，恢复备份会丢徽章、档案、推送订阅、编辑历史、邀请记录。
- `TABLES` 补全为 17 张：新增 `post_edits`、`badges`、`user_badges`、`user_profiles`、`push_subscriptions`、`invitations`。

### 14. 注册：重复账号报 500、昵称不限长
- 文件：`functions/api/auth/register.js`
- `INSERT users` 加 try/catch，把 UNIQUE 冲突转成 409「该账号已被注册」；昵称超过 16 个字直接 400。
- 注册时若带 `invite`，一次性结算邀请奖励，异常不影响注册；返回值增加 `inviteBonus`。

## 七、账号能力增强（本次新增，纯增量）

原本云端账号只能改头像和异人档案，**没有改昵称、改密码，也没有忘记密码的退路**。本次补齐三件事：

1. **用户自助改昵称**：账号页新增「保存昵称」；后端复用已有的 `POST /api/users/:id/profile`（新增可选的 `name` 字段），改完同步 `posts.author_name`、`replies.author_name`，历史帖子不会还挂着旧昵称。登录账号 `login` 不可改。
2. **用户自助改密码**：新增 `functions/api/auth/password.js`，先校验当前密码（PBKDF2 常数时间比对）再重设 hash + salt；新密码至少 6 位，且不能与旧密码相同。
3. **管理员重置他人密码**：`POST /api/users/:id` 新增 `action:'resetpass'`，成员管理列表每行多一个「🔑 重置密码」。这是没有邮箱/手机号的情况下、忘记密码的唯一找回路径。

兼容性（对照「不影响已经注册的人」）：

- **零 schema 变更**：没有加列、没有改表、没有新索引；本次只新增 1 个函数文件，其余都是在已有文件里加字段和界面。
- **密码哈希与 token 格式完全未动**：仍是 PBKDF2-SHA256 / 100000 轮 / 256 位，salt 仍是 `crypto.randomUUID()`；token 结构、签名密钥、30 天有效期不变，**已登录的用户不会被踢下线**。
- **改名只写 `users.name`**，不动 `login` / `points` / `pass_hash` / `salt` / `role` / `created_at`；其他用户的数据完全不受影响。
- 历史通知里的 `actor_name` 是快照，不回改（避免批量改写通知表），需要的话可以后续再做。

已知限制：改密码后，该用户在其它设备上已签发的 token 仍然有效（没有会话表，无法单点踢人）。要做到「退出所有设备」需在 `users` 增加 `token_version` 列、在鉴权时比对，属于可选下一步；本次没有动全站鉴权热路径。

验证：42 个 JS 全部 `node --check` 通过；改昵称 / 改密码的 UPDATE 语句在 SQLite 实测通过（并逐列断言老用户其余字段未变）。

## 八、徽章炫彩效果扩展（+2 种）

原有 6 种（0 金辉 / 1 紫电 / 2 烈焰 / 3 青碧 / 4 彩虹 / 5 银辉）都是亮色渐变 + 统一白色扫光，整体偏同一路。新增两种方向不同的：

- **6 墨曜（深色星砂）**：深墨蓝黑底 + 两团蓝紫雾光 + 六点星砂明暗闪烁，是全站唯一的深色徽章效果，和六种亮色系一眼能分开。
- **7 烟粉（呼吸光晕）**：粉白渐变 + 呼吸式光晕，并主动关掉全站统一的白色扫光——因为扫光正是「彩虹/银辉」最显眼的特征，关掉后才不会撞脸。

实现方式（沿用项目已有的安全边界）：

- 只改 `_lib.js` 里 `BADGE_EFFECTS` 这个纯字符串校验数组（`'0'..'5'` → 追加 `'6','7'`），**没有碰 `BADGE_SEEDS`**——历史上往徽章种子里加东西会导致 `ensureSchema` 失败、全站 500。
- 新样式单独放在 `assets/css/badge-effects-extra.css`，不改 `main.css`（不覆盖线上大文件），在 `index.html` 里追加一行 `<link>`。
- 前端只在 `BADGE_EFFECT_OPTIONS` 里加两项，徽章管理弹窗的色卡从 6 个变 8 个。
- 效果继续走原有变量机制（`--be-bg / --be-ink / --be-edge / --be-glow`），所以小徽章、徽章墙、发放格、管理列表行四处展示会自动生效，不需要改渲染函数。

注意：老访客如果还加载着旧 CSS，带新效果的徽章会暂时显示成无底色，`?v=40` 刷新后正常；**已创建的旧徽章完全不受影响**，新效果只在管理后台新建或编辑徽章时可选。

### 2. 回帖与楼中楼显示徽章（bug 修复）

现象：发帖的时候作者徽章正常，回复 / 楼中楼里没有。

排查结果：后端其实一直在返回 —— `_lib.js` 的 `shapeReplyList` 里有 `authorBadge:info.badge||null`，`userInfoMap` 也会批量取佩戴中的徽章；前端 `rootHtml`（顶层回答）与 `subReplyHtml`（楼中楼，递归子回复）模板里也都写了 `${badgeHtml(...)}`。

真正的原因在前端**取数据后重组对象**时把字段丢了：`app.js` 里有两处把接口返回的 reply 逐字段抄进本地对象，字段表是手写的，两处都漏了 `authorBadge`：

- 帖子详情首屏渲染那处（`replies=(d.replies||[]).map(...)`）
- `cloudRerender()` 里重新拉数据那处（`replies=(d.replies||[]).map(...)`）

所以徽章在"刚发帖、数据还是接口原样"的时候能显示，一旦重新渲染就消失。修复就是在两处映射各补一个 `authorBadge:r.authorBadge||null`，模板不用动，顶层回答和楼中楼（含更深层子回复）会一起恢复显示。
